1 简介

1.1 目的

本文档给出GORM V1适配KingbaseES MySQL兼容模式和Oracle兼容模式的概要设计。设计将兼容需求映射为明确的软件边界、扩展接口、模块职责、运行流程和测试标准，为开发、评审、联调、验收及后续版本升级提供共同依据。

本文档重点回答两个层次的问题：第零层确定采用一套代码、多个分支还是插件扩展，以及是否具备社区合入条件；第一层在总体方案下逐项分解连接、类型、SQL、DDL、元数据、事务和测试等兼容点。

1.2 范围

本期范围包括：

  • 保留GORM V1既有CRUD、回调、Scope、迁移和事务主流程。
  • 通过GORM公开的Dialect接口和RegisterDialect注册机制接入KingbaseES。
  • 提供kingbase-mysql和kingbase-oracle两个显式方言入口。
  • 适配参数占位符、标识符引用、数据类型、分页、主键回填、DDL和系统目录查询。
  • 提供单元、竞态和真实数据库集成测试入口。

本期不负责把业务应用中的手写SQL自动翻译为另一种数据库语法，也不负责业务模型、业务表结构和业务数据迁移。PG、SQL Server模式虽在当前适配包保留扩展入口，但不属于本期MySQL/Oracle验收范围。

1.3 设计依据

文档结构和深度参考金仓二期PowerJob、Flowable、Trino三个设计文档及甲方批注意见，特别落实以下要求：

  • 介绍框架预留的抽象类和接口，说明如何在不侵入核心逻辑的前提下注入数据库能力。
  • 说明框架目录结构、一级模块职责和整体主流程。
  • DB相关模块应说明类/文件职责、核心实现、子流程及系统目录查询含义。
  • 第零层必须确定总体兼容形态和社区合入策略；第一层必须覆盖全部兼容点。
  • 每一个已界定的问题必须有对应方案、责任模块和验收手段。

4 原有设计

4.1 GORM V1整体设计思想

GORM V1采用“公开API + 回调管线 + Scope SQL构造 + Dialect差异注入”的结构。业务代码面向*gorm.DB调用统一API；CRUD操作进入Callback管线；Scope基于模型元数据构建SQL；Dialect只负责与数据库产品相关的部分；最终由database/sql执行。

与本适配直接相关的框架扩展点如下：

扩展点接口/方法框架职责适配层职责
方言注册RegisterDialect(name, dialect)按名称保存方言原型，打开连接时创建实例。注册MySQL/Oracle两个明确名称。
方言契约Dialect定义类型、标识符、分页、迁移和元数据接口。实现或委托全部方法，不改变接口。
模型类型解析ParseFieldStructForDialect解析Go类型和gorm标签。把解析结果转换为Kingbase模式类型。
SQL上下文Scope组合字段、条件、变量和SQL。通过Dialect钩子提供差异片段。
CRUD生命周期Callback编排事务、关联、时间戳、执行和回调。不替换核心回调，仅改变方言输出。
驱动边界SQLCommon统一*sql.DB与*sql.Tx的执行接口。由gokb实现协议和参数处理。

4.2 目录结构与一级模块职责

目录/文件组职责与适配关系
main.goDB门面、Open、CRUD入口、事务和迁移API。通过方言名创建适配实例。
dialect.go、dialect_*.go方言接口、注册表及原生MySQL/PostgreSQL实现。提供标准扩展契约和可复用基线。
scope.go表名、字段、条件、参数、查询、DDL和AutoMigrate SQL构造。调用Quote、BindVar、DataTypeOf等接口。
callback*.goCreate/Query/Update/Delete回调链和事务边界。保持不变，验证适配SQL可通过既有回调执行。
model*.go、field.go模型反射、字段标签、主键和关联关系。为类型映射和DDL提供输入。
kingbase/dialectsKingbase方言注册、模式分派、类型、DDL和元数据覆盖。本期核心实现。
kingbase/test各模式真实库集成测试。本期验收入口。

4.3 原有核心流程

业务调用
db.Find/Create/AutoMigrate		→Callback或迁移入口→Scope构造SQL与参数→Dialect输出差异片段→database/sql执行

这一流程说明GORM V1已把数据库差异集中在Dialect接口，适配KingbaseES无需修改业务API、Callback主链和模型反射逻辑。

4.4 数据表和ER图适用性

结论：GORM是通用ORM框架，本身不拥有固定业务表，也不定义业务实体之间的ER关系，因此本设计不绘制业务ER图。应用表结构由接入方Go模型决定。适配层只读数据库系统目录，不创建或修改系统目录对象；其查询含义在6.2.3.8逐项说明。

6 概要设计

6.1 第零层设计描述

6.1.1 软件系统上下文定义

6.1.1.1 系统边界

本设计将“GORM V1核心 + Kingbase方言适配包”定义为待设计系统。业务应用、Go标准库database/sql、gokb驱动和KingbaseES数据库属于外部实体或外部依赖。

Kingbase方言适配包模式相关类型、SQL片段、DDL和元数据查询本设计的核心新增模块。
database/sql与gokb连接、参数绑定、执行、结果解码连接GORM与KingbaseES。

接口形式约束

6.1.2 设计思路

6.1.2.1 设计要点问题界定

  1. 总体形态：一套源码、两套源码、修改核心或插件/方言扩展中选择可维护方案。
  2. 模式边界：MySQL和Oracle在引用符、类型、分页、DDL、主键和系统目录上存在差异，不能用一个无边界的SQL替换器处理。
  3. 扩展机制：必须复用GORM V1预留的Dialect契约，不改Callback、Scope和业务API。
  4. 模式选择：ORM方言选择必须稳定、可测试，并能在配置错误时尽早暴露。
  5. 社区合入：实现应与上游公共接口兼容，交付不能依赖上游是否接收。
  6. 升级和回归：模式差异需要集中、可追踪，并可分别执行测试。

6.1.2.2 设计方法选择

选择GORM V1提供的Dialect扩展机制。适配包实现完整Dialect契约，并在内部复用成熟的MySQL或PostgreSQL方言作为基线，只覆盖KingbaseES存在差异的行为。

MySQL模式复用GORM MySQL方言的反引号、问号参数和分页基线；Oracle模式因GORM V1没有内置Oracle方言，复用PostgreSQL的编号参数和RETURNING执行链，再覆盖Oracle标识符、类型、分页、DDL、DUAL和兼容视图查询。

6.1.2.3 可选方案分析

方案描述优点缺点结论
A 修改GORM核心在Scope/Callback中加入Kingbase条件分支。短期直接。侵入核心、升级困难、难以社区合入、回归范围大。不采用
B 两套GORM源码MySQL和Oracle各维护一个fork。模式隔离。公共缺陷需重复修复，业务接入和版本管理复杂。不采用
C 单一方言运行时自动识别一个方言名，连接后探测模式并动态分支。配置项少。GORM SetDB不能返回错误；错误模式可能延迟到业务SQL才暴露；测试边界不清晰。不采用

6.1.2.4 社区生态与合入策略

适配实现仅使用GORM公开的RegisterDialect和Dialect接口，不改变公共API，技术上可作为独立方言包分发，也具备向上游提交的代码边界。实际是否合入由上游维护策略和评审结果决定，不作为甲方交付前置条件。

交付时优先保持kingbase/dialects为独立、低耦合模块；若后续拆分为独立Go Module，只需调整导入路径和驱动版本，不改变业务调用模型。

6.1.3 确定的第零层设计方案

D0-01方案结论：采用“一套GORM V1主干 + 一个Kingbase方言扩展包 + 两个显式模式入口”的总体架构。业务通过kingbase-mysql或kingbase-oracle选择策略；适配层不在每条SQL上探测模式；启动验收通过SHOW database_mode校验配置和实例一致性。
业务API层保持*gorm.DB、模型和gorm标签不变。
GORM核心层复用Open、Callback、Scope、AutoMigrate和Transaction流程。
适配路由层KingbaseDialect集中实现注册、模式路由、公共委托和连接实例隔离。
模式策略层dialect_mysql.go与dialect_oracle.go分别承载模式差异。
驱动层gokb负责连接、占位符归一化、协议和类型解码。
数据库层KingbaseES以MySQL或Oracle兼容模式执行SQL。

6.1.5 设计约束

  • 方言选择必须显式，且必须与SHOW database_mode结果一致。
  • 不改变GORM V1 Dialect公共接口和业务API。
  • 遵循Go database/sql接口；驱动使用甲方批准的gokb正式版本。
  • Oracle分页、identity、boolean、MODIFY和RETURNING受KingbaseES目标版本及兼容配置影响，必须执行真实库验收。
  • GORM V1 AutoMigrate只创建缺失表/列/索引，不删除列，也不自动完成破坏性结构变更。
  • 业务手写Raw SQL不由适配层翻译，调用方应编写目标模式可执行的SQL。

6.2.1.2 实现原则

  • 公共优先：模式无关逻辑放在KingbaseDialect，只在存在真实差异时进入模式文件。
  • 委托优先：GORM原生方言已经正确实现的行为直接委托，减少重复代码。
  • 显式优先：方言名和实际数据库模式不一致时失败，不做隐式回退。
  • 结构化优先：使用Dialect和模型解析API生成SQL，不用全局字符串替换。
  • 测试隔离：MySQL和Oracle用例独立运行，失败SQL可定位到具体兼容点。

6.2.2 整体流程

6.2.2.1 方言加载和连接流程

导入kingbase/dialects→init/Register注册两个方言→gorm.Open创建gokb连接→newDialect克隆方言→SetDB绑定连接并Ping
  1. 应用选择DialectKingbaseMySQL或DialectKingbaseOracle。
  2. GORM通过驱动名kingbase调用sql.Open。
  3. GORM从注册表创建Kingbase方言实例，适配层再克隆对应的原生基线方言。
  4. 每个方言实例绑定自己的SQLCommon，避免连接间共享可变DB句柄。
  5. 集成环境执行SHOW database_mode，不一致时终止测试或应用启动。

6.2.2.2 CRUD流程

业务模型与条件→CRUD Callback→Scope解析字段/条件→Dialect引用、绑定、分页→gokb执行并Scan

Create时，Callback根据LastInsertIDReturningSuffix决定调用Exec + LastInsertId还是QueryRow + Scan。Query时，Scope在prepareQuerySQL中组合SELECT、条件、排序及分页，结果通过字段映射写回模型。

6.2.2.3 AutoMigrate流程

读取模型结构→HasTable/HasColumn查询目录→DataTypeOf映射字段→CREATE/ALTER/INDEX→再次查询验证

不存在表时，Scope根据全部普通字段生成CREATE TABLE和主键，并创建标签声明的索引；表存在时仅添加缺失列和索引。显式ModifyColumn由Oracle策略生成ALTER TABLE ... MODIFY ...。

6.2.2.4 事务流程

Begin/BeginTx→克隆DB和方言→Dialect绑定*sql.Tx→执行CRUD→Commit或Rollback

6.2.3 分解及依赖性描述

6.2.3.1 适配注册与路由模块

文件：kingbase/dialects/dialect.go

职责：定义模式和方言常量；注册方言；为各模式选择基线方言；实现公共接口委托；将类型、DDL和元数据调用路由到模式策略。

关键类/结构：KingbaseDialect保存mode、当前SQLCommon和私有raw Dialect；四个轻量包装类型在SetDB时固定模式。

设计决定：未知模式按PG入口构造，但业务接入只使用公开常量；MySQL和Oracle不得通过连接失败自动互相回退。

6.2.3.2 连接与模式一致性模块

GORM的方言名决定ORM SQL策略，gokb读取数据库实际database_mode决定协议类型解码。两者是不同层次，必须一致。集成测试在连接和Ping成功后执行：

SHOW database_mode

返回值不是期望的mysql或oracle时直接失败，禁止继续执行DDL。生产应用应采用相同的启动健康检查。

6.2.3.6 DDL与迁移模块

建表和加列由GORM Scope统一生成，差异集中在DataTypeOf。Oracle字段修改单独生成：

ALTER TABLE "schema"."table" MODIFY "column" varchar2(128)

表、schema和列分别引用，防止保留字和大小写导致语法错误。索引创建仍走GORM公共流程；删除索引复用基线方言。AutoMigrate只做增量补齐，不负责删除字段、数据转换和跨版本迁移脚本。

6.2.3.7 主键生成与回填模块

MySQL模式把常见auto_increment映射为serial/bigserial，Create Callback执行INSERT后从驱动结果读取LastInsertId。Oracle模式用identity类型生成主键，并沿用GORM PostgreSQL基线的RETURNING查询回填链路。

验收要求：identity语法、RETURNING语法及驱动Scan行为必须在甲方目标KingbaseES版本上联合验证。若目标版本只支持序列方案，应在Oracle策略内集中替换，不得修改业务模型或Create Callback。

6.2.3.8 元数据发现与系统目录语义

GORM Dialect的HasTable/HasColumn/HasIndex/HasForeignKey返回bool，无法直接返回查询错误。因此Oracle路径先查询兼容视图；视图无权限或不存在时回退到Kingbase原生目录；两者都失败时返回false，并由后续DDL执行错误暴露根因。

功能MySQL模式查询对象Oracle模式（当前schema）Oracle模式（显式schema）查询含义
HasTableinformation_schema.tablesuser_tablesall_tables，owner过滤确认目标业务表是否存在，决定CREATE或ALTER路径。
HasColumninformation_schema.columnsuser_tab_columnsall_tab_columns确认模型字段是否已落库，决定是否ADD COLUMN。
HasIndexpg_indexesuser_indexesall_indexes防止AutoMigrate重复创建同名索引。
HasForeignKeyinformation_schema.table_constraintsuser_constraintsall_constraints筛选constraint_type='R'，确认外键约束是否存在。

所有查询都使用参数绑定，schema、表、列、索引和约束名称不直接拼入WHERE条件。适配层只读这些视图，不执行INSERT、UPDATE或DELETE。

6.2.3.9 事务与异常处理模块

  • 显式事务通过Begin/BeginTx创建*sql.Tx并重新绑定克隆后的方言。
  • Create/Update/Delete默认Callback在操作前开启事务，根据Scope错误提交或回滚。
  • 驱动连接、SQL执行和Scan错误写入DB.Error，保持GORM V1原有错误传播规则。
  • 适配层不实现自动重试，避免在非幂等事务中重复执行。连接重试由应用和连接池策略负责。

6.2.3.10 并发与实例隔离模块

GORM注册表中的方言对象是原型。若Kingbase方言直接保存gorm.GetDialect返回的全局MySQL/PostgreSQL对象，后一次SetDB会覆盖前一连接的DB句柄。设计要求ensureRaw按类型反射创建新的基线方言实例，再绑定当前连接。

该机制保证不同数据库连接、事务克隆和并行测试之间不共享底层方言的可变连接状态。验收包含双连接指针隔离测试和go test -race。

6.2.7 已知限制和后续扩展

  • Oracle模式的兼容语法需根据甲方实际KingbaseES小版本形成冻结矩阵。
  • Dialect元数据接口返回bool，不能完整表达权限不足、连接失败与对象不存在三种状态；需要更强诊断时可新增不影响GORM接口的适配包诊断API。
  • 复杂Oracle序列、触发器、函数索引、分区表和存储过程不在GORM V1通用AutoMigrate能力内。
  • 后续新增模式时应新增独立策略文件、注册名和测试矩阵，不在现有策略内堆叠无关条件分支。
